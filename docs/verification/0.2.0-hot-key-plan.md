# 0.2.0: hot-key commit path, pre-registered A/B plan (R-112)

Status: plan, committed before any measurement of the candidate. Results
go to a separate report; this file is changed only to record deviations
(dated, with the reason), never to move a target after data was seen.

## 1. Problem (measured in Phase 4.1)

64 writers PUT one key through four gateways: about 65 acknowledged PUT/s
of about 145 attempted, 54–55 % answered `503 SlowDown`, a SlowDown after
about 550 ms ([phase-4.1-r112.md](phase-4.1-r112.md) §2). The metadata
benchmark shows about 60 transaction attempts per operation on one hot
key ([phase-4.0-scalability.md](phase-4.0-scalability.md), "overwrite,
one hot key"). Cause (code analysis): `commit_put` reads the key's current
pointer, so concurrent commits on one key conflict; `transact` retries a
conflict immediately, up to 32 attempts
(`crates/metadata/src/kv.rs`, `transact_inner`); exhaustion is
`TooManyRetries`, answered SlowDown (`crates/gateway/src/cluster/backend.rs`,
`meta_err`).

## 2. Arms

- **tag rebuild**: the `v0.1.0` tag commit, rebuilt on the test host
  with the same toolchain (`rust-toolchain.toml`), profile (release) and
  features (`fdb`) as the candidate. Labelled "tag rebuild" everywhere:
  it is not the published artefact, and no statement about the published
  artefact is made from it.
- **candidate**: the head of the PR branch that implements the approach
  under test (§4), same build settings.

Each binary's SHA-256 and the commit it was built from are recorded per
run. Both arms run the same `arcabench` (from the candidate's tree: the
generator and checker are not under test) and the same cluster layout.

## 3. Hypothesis and targets

Hypothesis: serialising commits to one key inside each gateway (a FIFO
queue per bucket and key) and backing off with jitter on the remaining
cross-gateway conflicts turns most refused hot-key PUTs into acknowledged
ones and removes most wasted transaction attempts, without weakening any
answer guarantee.

Targets (candidate against tag rebuild, means over the valid runs of each
scenario; every one fixed now):

| Metric | Scenario | Target |
| --- | --- | --- |
| SlowDown share of PUTs | `unv`, `ver` | at most half the tag rebuild's, and at most 25 % |
| metadata transaction attempts per acknowledged PUT (gateways' `arca_gateway_meta_txn_attempts_total` delta / acknowledged PUTs) | `unv`, `ver` | at most half the tag rebuild's |
| acknowledged PUT/s | `unv`, `ver` | at least 1.3 × the tag rebuild's |
| acknowledged PUT/s | `unv16` | at least 0.95 × the tag rebuild's (no regression) |
| SlowDown share | `unv16` | not above the tag rebuild's + 0.5 percentage points |
| PUTs still SlowDown after the writer's 3 retries | `retry` | not above the tag rebuild's |
| acknowledged PUT p95 and p99 | all four | reported; p99 at most 1.5 × the tag rebuild's in `unv16`; in `unv`/`ver` reported with the all-PUT p99 (a former SlowDown now waits) |
| unknown outcomes (500, other 503s, transport errors, timeouts) | fault-free scenarios | 0, as in Phase 4.1 |
| violations, definite failures visible | every run, both arms, incl. `fdbstall`, `gwkill` | 0 |

**Adoption rule**: the candidate is adopted only if every target holds
and no protection is weakened (the checker's violations and "definite
failures visible" stay 0; no R-114 answer test is changed or removed;
FoundationDB's conflict check stays the authority on commit order). A
non-improving or protection-weakening prototype is not adopted. At most
two approaches are tried: the first is §4; if it fails, the second and
last is folding the GET's map-version read into the manifest transaction
(a GET-side cost, a smaller expected gain), measured against the same
targets where they apply. If both fail, nothing is adopted and R-112
stays open with the data.

## 4. Approach under test (first)

Per gateway, a bounded FIFO commit queue per (bucket, key): PUT
(`commit_resolving`), DELETE without a version id and
CompleteMultipartUpload wait their turn before their commit; at most one
commit per key per gateway is in flight. The turn is held until the
answer's outcome is decided (through `commit_resolving`'s resolution).
A wait longer than the bound W, or a full queue, is answered SlowDown
before any commit attempt was made, and the pending generation is
aborted (SlowDown = not applied, R-114). Conflicts between gateways
remain and are retried with jittered exponential backoff. The lock table
is bounded and an entry is removed when nobody holds or waits for it.
Design record: ADR-0041.

## 5. Scenarios and runs

`arcabench contend` as in Phase 4.1 (64 writers, 8 readers, 60 s, 4 KiB
bodies, four gateways round robin; check after settling):

- performance: `unv` (one key), `ver` (one key, versioning), `unv16` (16
  keys), `retry` (one key, writers retry SlowDown 3 times, full jitter
  from 100 ms);
- correctness only (candidate; no performance target): `fdbstall`
  (FoundationDB SIGSTOP 12 s at about 15 s and 47 s) and `gwkill` (all
  gateways SIGKILL at about 20 s and 40 s, restarted).

At least 3 valid runs per arm and performance scenario; at least 2 valid
runs of each correctness scenario on the candidate. A fresh cluster per
run. Order rotated: round r runs the scenarios in the order shifted by
r, and within a scenario the arm that goes first alternates by round
(tag rebuild first in round 1).

## 6. Metrics recorded per run

From the generator's log and the checker: PUT outcomes (acknowledged,
SlowDown, unknown by cause), acknowledged PUT/s, PUT latency p50/p95/p99
(acknowledged and all), GET outcomes and latency, violations. From the
gateways' metrics endpoint (sampled every second): metadata transaction
attempts, conflicts, exhausted, unknown retries; the candidate's
commit-queue counters (waits, refusals, wait time). From FoundationDB's
`status json` (every 2 s): transactions started, committed and conflicted
per second, commit latency probe. CPU (per process and host) and RSS of
gateways, storage nodes and fdbserver (`pidstat`), host load and free
memory (the sampler).

## 7. Invalid runs

A run is invalid (kept, reported, not counted) if: a fault time falls
outside the run; a cluster process exits unexpectedly in a fault-free
scenario; FoundationDB is not healthy before the run; the generator host
is CPU-saturated (above 90 % for more than 10 s); another workload runs on
the hosts (the sampler shows processes not of this run); the host guard
limits are crossed (free memory below 1 GiB, free root below 3 GiB); the
binary's SHA-256 does not match its build record; the check does not
complete. Invalid runs are repeated within the limits of §8.

## 8. Limits

At most 5 hours of host time for all measurements of both approaches; at
most 64 writers; each run bounded by `timeout`; private FoundationDB and
own directories only. When a limit is reached the campaign stops and
reports what it has (Inconclusive where the minimum runs are missing).

## 9. Driver and recorded deviations

Driver: `benchmarks/linux/hot-key-ab.py` (tests:
`benchmarks/linux/hot_key_ab_test.py`). Recorded before any measurement
(2026-11-23):

- Layout on three hosts: HOST_A the private FoundationDB process and the
  controller, HOST_B four storage nodes and four gateways (as in Phase
  4.1), HOST_C the generator and checker (Phase 4.1 ran the generator
  with the controller): the same for both arms.
- Two invalid-run rules made explicit, as parts of "the check does not
  complete": the generator exiting with an error, and a scrub that does
  not complete.
- Settling before the check: at least 420 s after a fault scenario, then
  until no reclaim is pending, the GC backlog is empty and the nodes' live
  records are stable for 60 s, at most 900 s (an unsettled run is
  recorded as such, not invalid).
- Repeats of invalid runs: at most 2 per arm and scenario, within §8.

## 10. Control: the queue on against off in one binary (addendum, pre-registered 2026-11-24)

Committed before any control run. Purpose: the main campaign compared the
tag rebuild with the whole candidate, which also carries other main
changes (results §1); this control isolates the queue.

- **Arms**: one binary, the build of the final PR head (built on HOST_B
  as in §2; its commit and SHA-256 recorded); **queue-on** (default
  gateways) and **queue-off** (gateways with `--commit-queue off`:
  immediate conflict retries, no turns). Everything else identical.
- **Scenarios**: `unv`, `ver`, `unv16` as in §5 (64 writers, 8 readers,
  60 s, four gateways), a fresh cluster per run.
- **Runs**: at least 3 valid runs per arm and scenario; rotated order as
  in §5 (round r shifts the scenarios by r; queue-off first in odd
  rounds, queue-on first in even ones); invalid runs repeated at most 2
  per cell.
- **Invalid runs**: the rules of §7 and §9, unchanged.
- **Targets**: those of §3 for these scenarios, read as queue-on against
  queue-off: `unv`, `ver`: SlowDown share at most half of off's and at
  most 25 %, attempts per acknowledged PUT at most half, acknowledged
  PUT/s at least 1.3 ×; `unv16`: acknowledged PUT/s at least 0.95 ×,
  SlowDown share not above off's + 0.5 points, acknowledged p99 at most
  1.5 ×; unknown outcomes 0 in every run; violations, definite failures
  visible and scrub findings 0 in every valid run.
- **Limits**: at most 2.5 h of host time for the runs (the build not
  counted), at most 64 writers, the same per-run bound.
- **Reporting**: the result is reported whatever it shows, as an
  addendum to the results. Met targets attribute the gain to the queue;
  a target not met is reported as such (which part of the gain the queue
  does not explain) and the decision on ADR-0041 is returned to the
  coordinator. No target is changed after a control run.
