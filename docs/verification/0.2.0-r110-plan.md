# R-110 for 0.2.0: capacity-pressure retest campaign plan

Status: **plan, no run made** (2026-11-24). A new campaign for the 0.2.0
binary; the 0.1.0 campaign's runs, approvals and results
([plan](phase-4.1-r110-retest-plan.md), [results of 2026-11-22](phase-4.1-r110-retest-results-2.md))
are closed and are not reused. This file is changed only to record
deviations (dated, with the reason) and the runs' records, never to move
a criterion or a limit after a result was seen.

The campaign runs [plan version 3](phase-4.1-r110-retest-plan.md) with
the amendments of §4, each stated with its reason and source before any
run. Everything not named in §4 is version 3 unchanged. As before, a
passed run verifies the small-allotment step only (plan §3); it does not
by itself close R-110.

## 2. Why a new campaign

The 0.2.0 binary changes what stage 7's scrub reports (ADR-0036), what a
storage node accepts (ADR-0037, ADR-0039) and how the gateway commits a
PUT (ADR-0041). The 0.1.0 results say nothing about this binary: run 2
passed on an earlier 0.1.0 candidate, run 3 on the final 0.1.0 binary was
Inconclusive. The amendments of §4 are needed to judge the 0.2.0
behaviour at all, and are fixed here before any 0.2.0 run.

## 3. The campaign

- **At most three main runs.** Run IDs `r110-020-<n>-<UTC time>`
  (`r110-020-1-20261125T010000Z`), `n` the main run's number, 1 to 3. The
  driver refuses any other ID for a preflight or a run, and a fourth
  main run (`driver.CAMPAIGN_RUN_ID`, `CAMPAIGN_RUNS`). The 0.1.0
  format (`r110-<UTC time>`) is accepted only by `collect` and
  `teardown`, for leftovers of that campaign. An attempt that never
  reached a host (the operator's command failed before any connection)
  does not count, as in the 0.1.0 campaign, and its `n` is used again
  with a new time; an attempt that connected counts, whatever its
  outcome.
- **New approvals only.** Each preflight and each run needs its own
  approval file naming the configuration's sha256, as before, and now
  also `"campaign": "0.2.0"` and `"campaign_run": <n>`
  (`driver.check_campaign_approval`). An approval of the 0.1.0 campaign
  has neither, and its configuration's run ID is refused: none can be
  reused.
- **Before each rerun** (run 2 and run 3), the previous run's cause, the
  change and the hypothesis are recorded in the new run's approval
  (`rerun`: `previous_run_id`, `cause`, `change`, `hypothesis`, each
  non-empty; `previous_run_id` names main run `n − 1`) and in the run's
  evidence on the operator's machine, before the run starts. The driver
  refuses an approval for run 2 or 3 without them. A rerun never loosens
  a criterion, a limit or a value after a result was seen; a change of
  this plan is a new dated section here, before the run it applies to.
- **One run kept for the final candidate.** Each approval says whether
  the binary is an `interim` candidate or the `final` one. Run 3 can only
  be the final candidate's (the driver refuses `interim` for it): runs 1
  and 2 may be spent on earlier candidates, the last one never.
- **The binary is the extracted candidate archive.** The binary under
  test is the one extracted from the candidate's release archive
  (`deploy/release/package.sh`), not a development build. The
  configuration records the archive's sha256 (`binary.archive_sha256`,
  required), the binary's sha256 and the commit; the preflight compares
  the binary on host 2 with the recorded sha256; the result reports all
  three.

The values of §1 and §4 are fixed by this file's commit; the approval of
each run names that commit (§6).

## 4. Amendments for 0.2.0

### 4.1 Stage 7's scrub: findings by per-shard class

Change. From a 0.2.0 binary the scrub classifies each shard (ADR-0036,
PR #45) and prints `retained … retained_damaged … in_flight …
unclassified …` after its findings. In C5:

- **Not findings:** `retained` (a record deleted and kept for the
  reclaim retention) and `in_flight` (a shard of a migration copy before
  its switch, of a pending write, or of a generation being collected).
  They are recorded with the result.
- **Findings, each failing C5:** every count of the eight finding
  classes, settled or not: an unexpected shard (now an orphan only),
  every damage class, a damaged retained or in-flight record (counted
  under its damage class, ADR-0036 §3), stale epoch, metadata/data
  mismatch, unrecoverable. A finding fails C5 also when another group's
  scrub reported errors or gave no result.
- **Never a pass, Inconclusive:** `unclassified` shards (counted as scrub
  errors: something could not be established, ADR-0036 §2), any other
  scrub error, a group without a result, or a scrub that printed no
  per-shard classes (not a 0.2.0 binary).
- **v3's count rule does not apply** (unexpected shards no more than the
  records pending reclaim, Inconclusive before the settle). Stage 7's
  settle wait stays: it is what removes legitimate orphans (a write
  diverted to another group, a `begin_put` still being retried) before
  the scrub (plan §7, ADR-0036 §1).

Reason: run 1 of 2026-11-22 failed C5 on 1,809 unexpected shards that
were most likely records kept for the retention (results §2); 0.2.0 tells
them apart per shard, so the count rule's excuse is no longer needed and
would hide orphans.

Tooling: `judge._c5_campaign`; `remote.SshCluster.integrity` scrubs every
group even after one with errors and keeps their classes
(`scrub_errors`, `scrub_unread_groups` in the timeline). Before this
change the harness stopped at the first group with an error, so a finding
in a later group gave Inconclusive instead of Failed.

### 4.2 Schema 5 and strict write ownership

Change. A cluster 0.2.0 initialises is at metadata schema 5 and its nodes
are strict from their first write (ADR-0037 §5, ADR-0039, PRs #48 and
#50): a node refuses any shard write that does not carry its cluster's
incarnation and name it. The run's cluster is new, so:

- **Precondition:** before stage 3's first write, every node reports
  `arca_node_write_ownership_strict` 1 and the controller
  `arca_controller_nodes_write_ownership_lenient` 0 (waited for at most
  120 s); otherwise the run ends there (precondition not formed, never a
  pass).
- **Protection:** `arca_node_writes_unproven_total` above 0 in any sample
  stops the run at once and fails it, as the other protection counters
  (plan §6.2); a node whose strict gauge is not 1 in any sample from
  stage 3 to stage 7 fails it too; either not sampled over the run makes
  it Inconclusive (`protections_not_sampled`).
- No upgrade from 0.1.0 and no mixed versions are part of this campaign.

Reason: the plan's C5 and its protections assume one cluster's writers;
0.2.0 enforces that, and the run should show it held from the first
write rather than assume it.

Tooling: the three families are sampled (`remote.sampler_config`);
`driver.Run.s3` and `driver.Run.protection`; `judge.judge`.

### 4.3 The gateway's commit queue

Change. 0.2.0 gateways queue each key's commits (ADR-0041, PR #49; on by
default, `--commit-queue-wait-ms` 2,000, `--commit-queue-max-waiters`
256; the run keeps the defaults, plan §5). SlowDown keeps its meaning: a
queue refusal comes before any commit attempt, so nothing is applied,
and the ledger keeps treating every `503 SlowDown` as refused, not
applied, and not unknown. The R-110 load writes each key once at a time
(new keys, deletes of the oldest), so no contention is expected; a queue
refusal is not excused anywhere (C3a and C3b still fail on any refused
PUT in their windows). What changes is the attribution: a PUT refused by
the queue had streamed its body, so its shards were stored before its
pending generation was aborted, as a write a node refused for capacity.

- C1a and C1b: D1's reclaimed records (the lower bound, plan §8.3) are
  also reduced by 3 per queue refusal
  (`arca_gateway_commit_queue_refused_full_total` +
  `…_refused_wait_total`, from the samples just outside the interval);
  not sampled, no bound (Inconclusive).
- C2: if the queue refused any PUT during stage 5 (or that is not
  known), every refused probe PUT counts as adding one shard per node,
  like an acknowledged one (the stricter threshold), and the result lists
  the refusals as an approximate attribution.

Reason: without it, reclaims of queue-refused writes could be counted as
D1's, and their live bytes could lower C2's threshold.

Tooling: `judge._queue_refusals`, `d1_reclaimed_bound(queue=…)`, `c2`.

### 4.4 Content-MD5 and checksums: no amendment

0.2.0 gateways verify `Content-MD5` and `x-amz-checksum-*` when a request
carries them (PRs #59, #60). The R-110 load sends neither: its requests
carry `Content-Length` only (`r110/s3.py`, anonymous path-style, one
attempt per call), and its own read-back compares each body's sha256
(C5). Nothing changes; a `400 BadDigest` or `InvalidDigest` would be an
unexpected response, which stops the run. The 0.2.0 answer to
re-creating one's own bucket (`409 BucketAlreadyOwnedByYou`, PR #58)
does not arise: each smoke sub-run creates a bucket of its own and the
main run creates `r110` once, in stage 3.

### 4.5 A host reboot is recorded as such

The three test VMs share one virtualisation host, which rebooted all of
them on 2026-11-22 (0.1.0 run 3), on 2026-11-23 and on 2026-11-24 (about
09:38 host time, during the hot-key campaign:
[0.2.0 hot-key plan](0.2.0-hot-key-plan.md) §10.2). They are three
systems, not three failure domains. A reboot is never a stop:

- On host 2, unchanged from PR #54: setup records the boot ID, a process
  found gone after it changed is `cause: host-reboot`, an uncompared boot
  is "unknown" and the run cannot pass.
- New: the watchdog reads every host's boot ID each round; a change is
  the stop `host-reboot` (a monitor rule: the alarm, the services
  stopped, the run Inconclusive), also when the host came back within the
  60 s that would have made it `host-unreachable`; an unreadable boot ID
  is a monitor failure. The preflight reports each host's boot ID.

Tooling: `watchdog.CHECK_SCRIPT`, `Watchdog.round`, `common.REASONS`.

## 5. Preflight (its own approval, read-only)

As plan §10, on every host, with these additions:

- **Retained directories of every host.** The configuration records, per
  host, the sha256 of the listing (path, size, modification time;
  metadata only, nothing opened) of each `p41-*` and other retained
  directory found at the last listing (`retained_record`: host ->
  directory -> sha256; an empty record for a host with none). The
  preflight lists them again on every host and fails on any difference.
  Nothing in them is read, written or removed (their deletion is the
  maintainer's decision, outside this plan).
- **Free space on every host.** `/` ≥ 3 GiB on every host, the data
  mount ≥ 3 GiB on every host that has it, and host 2's data mount ≥
  12.2 GiB (§1), after the earlier out-of-space incident on HOST_B (not a
  run of this campaign). HOST_A's root file system is close to the floor:
  the watchdog stops the run if it falls below 3 GiB, whatever uses it.
- **The system FoundationDB untouched:** `status minimal` on hosts 1 and
  2, nothing else (`system_fdb_hosts`); no process, file or port of it is
  touched by any command of the run.
- The binary on host 2 against the approved sha256 (by the preflight);
  the archive's sha256 and the build record against the configuration
  (by the operator, before the approval: the tooling cannot read them
  from the binary).
- The boot ID of every host, recorded by the preflight. Before it, the
  operator checks that nothing of an earlier run or another work stream
  runs on the hosts (processes listed and identified; none stopped on a
  guess).

## 6. What the approval of run 1 contains

The preflight is approved first, on its own (scope `preflight`). The
approval of run 1 (scope `run`, and `collect`, `teardown` if wanted) is
a JSON file written by the approver, never by the tooling, with:

- `config_sha256`: the sha256 of the run's configuration, which itself
  carries: `run_id` `r110-020-1-<UTC time>`; `"campaign": "0.2.0"`; the
  binary's `commit`, `sha256`, `archive_sha256` and `features` `["fdb"]`;
  the settings and limits of §1 (or tighter ones); `fdb_memory` (and
  `fdb_cache_memory`) chosen at the preflight; `retained_record` of every
  host from the preflight's listing; `system_fdb_hosts` hosts 1 and 2;
  `optional_checks` as found at the preflight (none, or `kernel_log`,
  `swap` where unreadable); the teardown scope "the run's own directories
  and processes only".
- `scope`, `window_start`, `window_end` (UTC, at most 24 h, containing the
  run's 7.5 h and the 30 min drain from its start: the driver refuses a
  run that would end after the window), `approved_by`.
- `"campaign": "0.2.0"`, `"campaign_run": 1`, `"candidate"`: `"interim"`
  or `"final"`.
- Recorded with it (in the approval's notes and the run's evidence): the
  instruction it is written from (the maintainer's delegation of
  2026-11-23 allows up to three new R-110 main runs for 0.2.0; as in
  0.1.0, a value the maintainer did not review is said so in the
  results), the preflight's result file, and this plan's commit.

Run 2 and run 3 add `rerun` (§3).

## 7. What this plan does not change or claim

- No product change; no change of a format, a protocol or the schema.
- C1a to C4 and their values are version 3's; the amendments only judge
  what 0.2.0 reports and attribute what it does; none relaxes a
  threshold.
- R-110 stays open whatever the campaign gives (plan §3); what was not
  verified in 0.1.0 (D1's whole reclaim under a persisting refusal,
  larger allotments and object counts, more hosts, longer runs) is not
  verified by this plan either.
