# 0.2.0 three-host functional validation

Plan, expected behaviour (derived from the code at the source revision under
test) and fixed pass/fail rules for a functional validation of arca-lake
0.2.0 on three Linux hosts, followed by the results of each run. It extends
the [0.1.0 validation](0.1.0-three-host-validation.md): its steps 0 to 7c are
kept with their rules, the transport is now mutual TLS and FoundationDB TLS,
S3 requests are SigV4-signed, and steps for multipart uploads, R-117, R-119,
the ADR-0036 scrub classes and a separate upgrade scenario from the
published 0.1.0 are added. Driver:
[`benchmarks/linux/three-host-validate.py`](../../benchmarks/linux/three-host-validate.py)
(`run` for the main scenario, `upgrade` for the upgrade scenario) with the
ledger client
[`benchmarks/linux/three-host-client.py`](../../benchmarks/linux/three-host-client.py).

This plan was written before the first run on the code at `726e966`
(origin/main, 2026-11-24). Any change to a rule after the first run is
recorded in the Results with its reason. Like the 0.1.0 one, this is a
functional check of one small cluster, not a performance, durability at
scale or long-running test.

## Environment and layout

Three hosts, 4 CPUs, about 7.5 GiB RAM, no swap each, one LAN. **They are
three virtual machines on one virtualisation host: three operating systems,
not three physical failure domains.** Every fault below is a process signal,
a deleted directory, a flipped byte or a process at a reused address; no
host is powered off, no network is cut or partitioned, no disk is detached.

One release build (`cargo build --release --locked -p arca-lake --features
fdb`) on host B, copied to A and C and checked by SHA-256. The upgrade
scenario also uses the published v0.1.0 binary, from
`arca-lake-0.1.0-x86_64-unknown-linux-gnu.tar.gz` (archive SHA-256
`975c036c6fa0a479b2bd0a0e6c313fd0dc5d83bcfb29ed9a2f730f2611c8de83`, checked
before extraction; `BUILD-INFO.txt` names commit `5601018`).

| Host | Processes (main scenario) |
| --- | --- |
| A | private `fdbserver` (one process, `configure new single ssd`, own port, own data directory, TLS; the system FoundationDB is not used), controller `ctl-a`, storage nodes `a0`, `a1` |
| B | controller `ctl-b`, nodes `b0`, `b1`, gateway `gw-b`; for step 8 the second cluster's private `fdbserver` (plaintext) and controller `ctl-z` |
| C | nodes `c0`, `c1` (step 8c: `c2`), gateway `gw-c`, the S3 client; for step 8 the second cluster's node (the impostor) at `c1`'s address |

Everything of a run lives under one run directory per host (marker file
`.owner`); only processes whose pid file is there and whose command line
names that directory are signalled.

- Storage nodes, groups, controllers and gateways: as in 0.1.0 (§
  Environment and layout there): `--capacity-bytes 3GiB` (`c2` too since the change after c2-j1, before it 1 GiB),
  `--segment-max-bytes 64MiB`, labels `host=a|b|c`, `node=<name>`,
  `device_class=hdd`, registered a0, b0, c0, a1, b1, c1;
  `create-groups --count 2 --k 2 --m 1 --chunk-bytes 4194304
  --small-threshold 65536 --failure-domain host`; controllers
  `--failure-domain host --unhealthy-after-secs 20 --health-interval-secs 5
  --gc-interval-secs 10 --gc-grace-secs 30 --min-orphan-age-secs 90
  --reconcile-interval-secs 30 --admission-horizon-secs 60
  --admission-dwell-secs 10 --scrub-interval-secs 0`, no `--auto-repair`;
  gateways `--lease-secs 60`, same profile flags.
- **Transport.** One CA per cluster (`arca-lake tls init-ca` on host A), one
  trust domain. Every process gets a role certificate
  (`tls issue --role node|controller|gateway|admin|fdb`; node certificates
  are named by the node id, so nodes are registered before their
  certificate is issued and they are started). Node RPCs use mutual TLS
  (`ARCA_TLS_CA/CERT/KEY`, `ARCA_TRUST_DOMAIN`); FoundationDB listens with
  `:tls` and its server certificate, and every arca-lake process connects
  with its client certificate (`ARCA_FDB_TLS_*`, peers verified as
  `spiffe://<td>/fdb/`). No `ARCA_INSECURE_PLAINTEXT` and no
  `ARCA_FDB_INSECURE_PLAINTEXT` anywhere in the main cluster.
- **S3.** Gateways run with `--credentials-file` (two principals, `owner`
  and `other`, one key each, random secrets written on the client host
  only) and the default authorization (`owner-policy` with a credentials
  file and the cluster backend, `crates/cli/src/main.rs:491-496`), no
  `--allow-anonymous`. The client signs every request with SigV4 using
  botocore's `S3SigV4Auth` (botocore is installed on host C; its version is
  recorded) and sends it with `http.client`, so the outcome classification
  of the 0.1.0 ledger is unchanged. If botocore cannot be imported the
  client exits non-zero and the step FAILs: **a skipped check is never a
  pass**.
- Multipart: `--multipart-min-part-bytes` left at its default 5 MiB
  (`main.rs:539-542`).

The ledger, candidate sets and the violation rule are those of the 0.1.0
plan (§ The ledger and how outcomes are judged): **any violation in any step
is a FAIL**, and a FAIL stops the sequence (later steps NOT RUN, cluster torn
down, evidence kept).

## Expected behaviour from the code

What 0.1.0's plan derived (placement, writes need every shard, reads need
`k`, takeover within the lease, unhealthy and quarantine, FoundationDB
timeouts) still holds at `726e966`; the line numbers moved, the logic did
not (`crates/gateway/src/cluster/write.rs:990-991,1080`: `m_ack = m`). New:

- **Schema 5 and recorded failure domains (R-119, ADR-0038, ADR-0039).** A
  new 0.2.0 store initialises at schema 5 (`crates/metadata/src/keys.rs:58`,
  ADR-0039 §2.2), so `admin upgrade status` prints `schema Some(5)
  schema_write Some(5)` and `protections mandatory`
  (`crates/cli/src/main.rs:4542-4557`). Every group is created with its
  failure domain recorded in the same transaction
  (`crates/metadata/src/ops/cluster.rs:233-259`, source `created`), printed by
  `admin status` as `failure_domain group G label host source created`
  (`main.rs:2542-2550`); `admin group check` exits 0 when no group breaks
  or lacks its domain (`main.rs:3402-3425`). A member move keeps the
  recorded label (ADR-0038; `crates/controller/src/process.rs:3430`
  `choose_for`, `crates/placement/src/lib.rs:145` `choose_replacement`): in
  step 7b the only candidate for b1's slots is b0.
- **mTLS.** A node, controller, gateway or admin without TLS flags refuses
  to start unless plaintext is explicit (`main.rs:319-372`, `395-429`); a
  peer whose certificate is not from the trust bundle fails the handshake
  (ADR-0017), counted by `arca_node_tls_handshake_failures_total`.
- **R-117 (ADR-0037).** A node of a cluster initialised at schema 5 is
  strict from its first write: it takes a `PutShard` only when it carries
  the node's adopted incarnation and names this node
  (`crates/storage-node/src/service.rs:633` `check_write_incarnation`, `680`
  `check_write_target`); refusals are `FAILED_PRECONDITION` (`incarnation
  rejected …`, `node rejected …`), which the gateway treats as a failed
  write of that member and places the chunk on another group
  (`crates/protocol/src/client.rs:2247` `is_incompatible`). So a node of
  another cluster at a reused address is (a) unreachable if its certificate
  comes from another CA (TLS handshake), (b) reachable but refusing every
  write if it shares the CA and trust domain but adopted the other
  cluster's incarnation. In both cases **no chunk is counted written on
  it**: every PUT acknowledged meanwhile has no chunk in a group of the
  replaced member. In case (b) the leader's health pass finds the other
  identity token for its id and quarantines the node ("the node holds
  another identity token for its id: another cluster's disk, or a
  re-registered id", `process.rs:1787-1810`); the real node, once back,
  needs `admin node rejoin`.
- **SigV4 and ownership.** Credentials file principals and keys
  (`crates/gateway/src/auth.rs:36-65,175`); an unknown access key is
  `InvalidAccessKeyId` (`auth.rs:711-714`); an anonymous request is denied
  (`auth.rs:763-770`); the bucket owner is the creating principal and
  another principal is denied on it (`auth.rs:909-950`, `917`). Signature
  checks are the s3s crate's (`SignatureDoesNotMatch`,
  `XAmzContentSHA256Mismatch`).
- **Body digests (added after the rehearsal for features merged since).**
  PutObject compares `Content-MD5` with the MD5 of the body as it streams,
  before the commit; a mismatch is `400 BadDigest` and the pending write is
  aborted (`crates/gateway/src/cluster/write.rs:173-190`,
  `crates/gateway/src/checksum.rs:114-130`). `DeleteObjects` is checked in
  the server layer after authentication and before the operation runs
  (`crates/gateway/src/server.rs:274-281`, scope
  `crates/gateway/src/xml_digest.rs:110-122`): an `x-amz-checksum-*` that
  does not match is `400 BadDigest` and nothing is deleted
  (`xml_digest.rs:63-86`). A body that does not match a signed
  `x-amz-content-sha256` is `400 XAmzContentSHA256Mismatch` and an owner's
  re-creation of its bucket `409 BucketAlreadyOwnedByYou` since #58
  (`crates/gateway/src/body.rs:37-40`, `cluster/backend.rs:1396`): the
  pre-registered step 2b rules, unchanged, are expected to pass now.
- **Scrub classes (ADR-0036).** The scrub line appends `retained …
  retained_damaged … in_flight … unclassified …` (`main.rs:5460`). Shards of
  deleted or overwritten objects are retired for the reclaim retention
  (86 400 s default) and count as `retained`, not findings;
  `UnexpectedShard` counts only orphans nothing references and no delete
  retired, which reconciliation removes once older than
  `--min-orphan-age-secs` (90 s); `in_flight` is what a running operation
  holds; `unclassified` is never healthy and counts in `errors` (0.1.0
  nodes only report it that way, ADR-0036 §6). After deletes and a quiet
  period longer than the orphan age plus a reconcile interval, a scrub of
  an all-0.2.0 cluster must therefore show `retained > 0` in total,
  `unclassified 0`, `in_flight 0`, `UnexpectedShard 0`, no damage, 0
  errors.
- **Upgrade from 0.1.0 (ADR-0039, `docs/guide/operations.md` § Upgrading
  from 0.1.0).** 0.1.0 initialises at schema 4 and reads `[3, 4]`; 0.2.0
  reads `[4, 5]`, so mixed processes run until the finalize. Groups created
  by 0.1.0 have no recorded failure domain: `admin group check` exits 1
  with `no recorded failure domain` and `degraded`; the finalize is refused
  until `admin group set-failure-domain --all-unrecorded --label host`
  records it, and while any 0.1.0 process or node takes part (`reads schema
  4` for processes, `0.1.0 or earlier` for nodes:
  `crates/controller/src/upgrade.rs:319-370`). Before the cut-off any
  process can go back to 0.1.0 (records unchanged). After the finalize: a
  0.1.0 controller and gateway refuse to start (startup gate,
  `crates/metadata/src/ops/compat.rs:157`); a 0.1.0 storage node is
  quarantined by the leader before it is sent anything and takes no counted
  write (`process.rs:1705-1732`); `admin node rejoin` refuses it until it
  runs 0.2.0.

## Judged runs

A judged run is started with `JUDGED=1` and `SOURCE_SHA` (the commit the
binary was built from). The driver refuses to start it if
`CONTINUE_ON_FAIL` or `STOP_AFTER` is set (both are script debugging
only), and refuses any run whose binary under test does not have one
SHA-256 on all three hosts, or, for `upgrade`, whose 0.1.0 binary is not
the published one (SHA-256 `c1cd2221…dd56`, `arca-lake 0.1.0`). A judged
run also needs `arca-lake --version` to print `arca-lake 0.2.0`
(`EXPECT_VERSION`) on every host. Each host's SHA-256 and `--version` are
recorded in `meta.json` and at the top of `results.md`. A judged run
tests the **release candidate archive** produced by
`deploy/release/package.sh`, installed by the driver's `install-candidate
<archive> <sha256>` command. The command checks the archive's SHA-256
against the value given, on the operator's machine and again on each host.
It extracts the archive in a fresh directory on each host and requires
`BUILD-INFO.txt`'s source commit to equal `SOURCE_SHA` and `--version` to
print `arca-lake 0.2.0`. It then installs the binary and writes the build
record `ROOT/bin/build-record.json` (kind `release-candidate`, archive
SHA-256, binary SHA-256, commit) from the archive. A judged run requires
such a record on every host, naming `SOURCE_SHA` and the installed
binary, with one archive SHA-256 on all three. The driver's `build`
command (a build of `git archive SOURCE_SHA` on host B, record kind
`rehearsal-build`) is for rehearsals only. Every `upgrade` run needs, on
every host, the archive downloaded by the driver's `fetch-v010` command,
whose SHA-256 is checked before anything reads it, whose `BUILD-INFO.txt`
names `5601018…`, and whose binary is the one installed. Every run needs
the put budget plus 5 GiB free on the file system of `ROOT` on every host.
Host A's `ROOT` must not be on its root file system. The candidate run
is two judged runs on the candidate binary, `run` then `upgrade`, each from
a fresh setup. A FAIL stops it.

## Load and window checks

Added before the judged run after an independent review of the rehearsal
(see Results). Every background load phase (steps 3a–8c, U2–U8) must end
with the client's exit status 0, no traceback in its log, no request the
client failed to build or sign (counted as `local-error`, never as
refused), and at least **20** acknowledged operations (PUT or DELETE
acked, GET answered as a candidate) through each gateway. Each judged
window must hold at least **3** acknowledged operations through each
gateway that serves in it:

- 3a b0 down; 3c host B's nodes down; 5 a1 down;
- 3b: gw-c while gw-b is down; gw-b from 5 s to 25 s after its restart;
- 4: each takeover cycle;
- 6: the 30 s after ready, for each of SIGSTOP and SIGKILL;
- 8a and 8b: the impostor at c1's address, from 10 s after its start;
- U2: from 10 s after each node's restart to the next stop, at least 25 s
  (since the change after c2-uj1);
- U3: each controller's restart, 25 s from it (since the change after
  c2-uj1; before, about 12 s);
- U5: the other gateway while one restarts; the restarted one from 5 s to
  25 s;
- U8: the 0.1.0 node at c1.

A step whose own rules pass but one of these checks fails is a FAIL.

The put budget for a whole run is 3072 MiB of logical PUT bytes. The
rehearsal's largest sequence wrote 1.65 GiB. If a PUT would pass the
budget, the client stops and exits non-zero, so the step FAILs: a load
never goes on without its writes.

## Not covered

- Host failure in the physical sense: the three hosts are VMs on one
  virtualisation host (one hardware and power failure domain); no power
  loss, no whole-host loss, no network partition or packet loss, no clock
  faults.
- FoundationDB with more than one process or its own failover (one process
  on host A: host A is a single point of failure).
- Certificate rotation, CRLs and expiry during the run; FoundationDB TLS
  for the second cluster of step 8 (plaintext, it is a test fixture).
- Bucket policies beyond ownership, presigned URLs, versioning, the cache

### Product findings (step 2b)

- **P1: a PUT whose body does not match its signed payload hash is
  answered `500 InternalError`**, not a 4xx. Reproduction: gateway with
  `--credentials-file` (cluster backend); sign `PUT /v3h/auth/gw-b` with
  botocore's `S3SigV4Auth` over plain HTTP for a 4097-byte body A

  body B with those headers. Both gateways answered `500`,
  `<Code>InternalError</Code><Message>body read failed:
  UploadStreamError: Sha256Mismatch</Message>` (gateway log `s3s::service`

  there is no data impact; but S3 answers `400 XAmzContentSHA256Mismatch`
  (or `BadDigest`), and SDKs and the ledger treat a 500 as a server fault
  whose outcome is unknown and retry it. Likely cause (code reading): every
  body stream error is mapped to `InternalError`

  Reproduced in dbg2, r1, r2, r3, dbg3–dbg6 (every run).
