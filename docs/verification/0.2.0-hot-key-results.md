# 0.2.0: hot-key commit path, A/B results (R-112, ADR-0041)

Status: campaign `hk20261124` complete, 28 of 28 runs valid. **Verdict per
the pre-registered plan ([0.2.0-hot-key-plan.md](0.2.0-hot-key-plan.md)):
adopt** — every target met, no protection weakened. All figures
**measured**; means over the valid runs of each cell.

## 1. Setup

- Arms (`build-record.json`): **tag rebuild** — the `v0.1.0` tag commit
  `5601018`, rebuilt on HOST_B with rustc 1.99.1, release, `--locked`,
  `--features fdb` (not the published artefact); **candidate** — commit
  `b4a6a40` of the PR branch, same build. Later commits of the branch
  change only the driver, its tests, a test file and documents (no
  server code).
- Layout (plan §9): HOST_A a private FoundationDB process and the
  controller, HOST_B four storage nodes and four gateways, HOST_C
  `contend` (64 writers, 8 readers, 60 s, 4 KiB bodies, gateways round
  robin). A fresh cluster per run.
- Driver `benchmarks/linux/hot-key-ab.py`; 28 runs in the rotated order
  of the plan, 2 h 51 min of host time (plus about 8 min of builds and one
  uncounted 5-min smoke run), within the 5 h limit.

Other observations:

- Transactions given up after 32 conflicts (`TooManyRetries`): about
  5,000 per run (tag, unv/ver) against 2–6 (candidate). The candidate's
  remaining SlowDowns are mostly turns refused at the 2 s wait bound
  (30–61 per run), answered before any commit attempt.
- **Latency of acknowledged PUTs on one hot key is higher** with the
  queue (p50 about 200 → 450 ms, p99 about 0.8 → 1.7 s): writes that
  were refused after about 550 ms now wait their turn and succeed. The
  all-PUT p99 rises from about 1.1–1.2 s to 1.8 s; with SDK-like retries
  it falls (3.5 → 2.3 s). The plan sets no latency target for one key;
  on 16 keys p99 stays within its bound (548 against 520 ms).
- "Attempts per acknowledged PUT" is, as pre-registered, the gateways'
  transaction counter over acknowledged PUTs: it includes the readers'
  GET transactions in both arms, so it understates the change on the
  commit path. FoundationDB's conflicted transactions per acknowledged
  PUT fall from about 50 to 1.1.
- Correctness: 0 violations, 0 definite failures visible, every scrub
  without a finding (no unclassified shard), in all 28 runs including
  `fdbstall` and `gwkill`; every run settled.

## 4. Driver fixes and deviations

Found before the campaign, recorded in the commits (none after it began;
no run was repeated or discarded):

- the source archive was taken from `benchmarks/linux` (the first build
  found no `Cargo.toml`): archived from the repository root;
- the smoke run (candidate, unv; not counted, kept in `smoke/`) showed
  the generator's process unattributed (its command line named the run
  directory after 300 characters): processes are attributed on the whole
  command line;
- work areas on HOST_B moved to its data disk (`/mnt/arca-fdb/v020-perf`;
  its root had 11 GB free, the builds need more); the 5 GiB floor is
  checked before every run on the work areas' filesystems.
