# 0.2.0: hot-key commit path, A/B results (R-112, ADR-0041)

Status: campaign `hk20261124` complete, 28 of 28 runs valid. **Verdict per
the pre-registered plan ([0.2.0-hot-key-plan.md](0.2.0-hot-key-plan.md)):
adopt** — every target met, no protection weakened; the gain is that of
the whole candidate (§1, attribution). The on/off control in one binary
(plan §10, §6 below) met every target: the single-key gain is the
queue's. All figures **measured**; means over the valid runs of each
cell.

## 1. Setup

- Arms (`build-record.json`): **tag rebuild** — the `v0.1.0` tag commit
  `5601018`, rebuilt on HOST_B with rustc 1.99.1, release, `--locked`,
  `--features fdb` (not the published artefact); **candidate** — commit
  `b4a6a40` of the PR branch, same build.
- **Attribution (review correction).** The candidate is not v0.1.0 plus
  the queue: `b4a6a40` also contains the main commits merged before it
  (R-117 strict shard-write ownership, R-119 group failure domains,
  metadata schema 5, per-shard scrub classification, the tiering fix
  R-118), and the branch tip has more server code since (`726e9664`,
  R-117 follow-ups). The tag-vs-candidate comparison therefore attributes
  the gain to the **whole candidate**. The queue is the plausible cause
  by mechanism (conflicted FoundationDB transactions per acknowledged
  PUT fall from about 50 to 1.1, and `TooManyRetries` from about 5,000 to
  2–6 per run; none of the other changes is aimed at the metadata commit
  of a PUT), but this campaign does not isolate it. The unv16 differences
  (0.97 × PUT/s, 1.06 × p99, both within their targets) **cannot be
  attributed to the queue**: other changes in the candidate (for example
  the node-side ownership checks on every shard write) may account for
  them. A control with one binary, `--commit-queue on` against `off`, is
  pre-registered in the plan (§10) and reported whatever it shows.
- Layout (plan §9): HOST_A a private FoundationDB process and the
  controller, HOST_B four storage nodes and four gateways, HOST_C
  `contend` (64 writers, 8 readers, 60 s, 4 KiB bodies, gateways round
  robin). A fresh cluster per run.
- Driver `benchmarks/linux/hot-key-ab.py`; 28 runs in the rotated order
  of the plan, 2 h 51 min of host time (plus about 8 min of builds and one
  uncounted 5-min smoke run), within the 5 h limit.

Other observations:

- Transactions given up after 32 conflicts (`TooManyRetries`): about
  5,000 per run (tag, unv/ver) against 2–6 (candidate). The candidate's
  remaining SlowDowns are mostly turns refused at the 2 s wait bound
  (30–61 per run), answered before any commit attempt.
- **Latency of acknowledged PUTs on one hot key is higher** with the
  queue (p50 about 200 → 450 ms, p99 about 0.8 → 1.7 s): writes that
  were refused after about 550 ms now wait their turn and succeed. The
  all-PUT p99 rises from about 1.1–1.2 s to 1.8 s; with SDK-like retries
  it falls (3.5 → 2.3 s). The plan sets no latency target for one key;
  on 16 keys p99 stays within its bound (548 against 520 ms).
- "Attempts per acknowledged PUT" is, as pre-registered, the gateways'
  transaction counter over acknowledged PUTs: it includes the readers'
  GET transactions in both arms, so it understates the change on the
  commit path. FoundationDB's conflicted transactions per acknowledged
  PUT fall from about 50 to 1.1.
- Correctness: 0 violations, 0 definite failures visible, every scrub
  without a finding (no unclassified shard), in all 28 runs including
  `fdbstall` and `gwkill`; every run settled.

## 4. Driver fixes and deviations

Found before the campaign, recorded in the commits (none after it began;
no run was repeated or discarded):

- the source archive was taken from `benchmarks/linux` (the first build
  found no `Cargo.toml`): archived from the repository root;
- the smoke run (candidate, unv; not counted, kept in `smoke/`) showed
  the generator's process unattributed (its command line named the run
  directory after 300 characters): processes are attributed on the whole
  command line;
- coverage beyond plan §4 (recorded in ADR-0041 §6): every DELETE form
  takes the key's turn, not only DELETE without a version id; since the
  review they also back off after conflicts (a later commit than the
  measured one; the campaign measured PUT only);
- work areas on HOST_B moved to its data disk (`/mnt/arca-fdb/v020-perf`;
  its root had 11 GB free, the builds need more); the 5 GiB floor is
  checked before every run on the work areas' filesystems.

## 6. Control: the queue on against off in one binary (plan §10)

Campaign `hkc20261124`, pre-registered in plan §10 (amended in §10.1 and
§10.2 before resuming). One binary, built from main `d7df1106` (the
merged code; SHA-256 `738eba64…`, rustc 1.99.1, release, `--locked`,
`--features fdb`); arms **queue-off** (gateways with `--commit-queue
off`) and **queue-on** (default gateways); the layout and settings of
§1. **All targets of §10 met**: the gain on one key is the queue's.

Course of the campaign: runs 1–8 valid (07:27–08:11); run 9 (`unv16`,
queue-on) invalid: the operator machine lost its route to the hosts
during its check; runs 10–30 aborted at their first remote command, before

Reading:

- **Attribution.** With everything else equal, the queue alone gives the
  single-key effect seen in §2 (SlowDown about 54 % → under 3 %,
  acknowledged PUT/s 1.3–1.6 ×, FoundationDB conflicts per acknowledged
  PUT about 49 → 1.1), and the latency cost (acknowledged p50 about
  190 → 450–480 ms, p99 about 0.8 → 1.8–1.9 s).
- **unv16.** Queue-on is 1.05 × queue-off (517 against 490 PUT/s): the
  0.97 × of the main campaign (tag rebuild against candidate) is not the
  queue's; it belongs to other differences between v0.1.0 and the
  candidate, or to run-to-run variation.
- **`ver` varies most.** Queue-on per run: 121.6, 100.1 and 76.8 PUT/s
  (SlowDown 0.4 %, 2.0 %, 5.4 %); the mean meets its target by a small
  margin (1.34 × against 1.3 ×), the last run alone would not (1.03 ×).
  That run is the only `ver` queue-on run after the reboot, so it is
  confounded with the fresh-boot condition (§10.2) and with
  run-to-run variation; this control cannot separate them. Queue-off
  `ver` was steady (73.4–76.0), as were both arms of `unv` and `unv16`
  across the reboot (`unv` queue-on 112.1 before, 106.3 and 116.6
  after).
