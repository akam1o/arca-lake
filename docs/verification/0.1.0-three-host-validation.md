# 0.1.0 three-host functional validation

Plan, expected behaviour (derived from the code at the source revision under
test) and fixed pass/fail rules for a functional validation of arca-lake on
three Linux hosts, followed by the results of the run. Driver:
[`benchmarks/linux/three-host-validate.py`](../../benchmarks/linux/three-host-validate.py)
with the ledger client
[`benchmarks/linux/three-host-client.py`](../../benchmarks/linux/three-host-client.py).

This is a functional check of one small cluster, not a performance,
durability-at-scale or long-running test. The plan was written before the
first run. Changed after it, each recorded in the Results: the injection
and rule of step 7a (after r2), and, after an independent review of the
first results, three checks made stricter for the next run (steps 3c, 5
and 7a, marked "rerun" below).

## Environment and layout

Three dedicated hosts (4 CPUs, about 7.5 GiB RAM, no swap each, one shared
1 Gb/s-class LAN, clocks NTP-synchronised to within 2 ms at the start).
One release build (`cargo build --release --locked -p arca-lake --features
fdb`) on host B, copied to A and C (same SHA-256).

| Host | Processes |
| --- | --- |
| A | private `fdbserver` (single process, `configure new single ssd`, own port 4610, own data directory, `--memory 2GiB --cache-memory 256MiB`; the system FoundationDB on 4500 is not used), controller `ctl-a`, storage nodes `a0`, `a1` |
| B | controller `ctl-b`, storage nodes `b0`, `b1`, gateway `gw-b` |
| C | storage nodes `c0`, `c1`, gateway `gw-c`, the S3 client |

Why this layout: it is the suggested one; nothing in the code requires
another. Two controllers on different hosts are the documented minimum
(`docs/guide/operations.md`, "At least two controllers"). The client on C
reaches gw-c locally and gw-b across the network.

- Storage nodes: `--capacity-bytes 3GiB` (two nodes share each host's data
  file system; allotments that fit it, as in the quick start, instead of
  `--allow-shared-filesystem`), `--segment-max-bytes 64MiB`, defaults
  otherwise. Labels `host=a|b|c`, `node=<name>`, `device_class=hdd`,
  registered in the order a0, b0, c0, a1, b1, c1.
- Groups: `create-groups --count 2 --k 2 --m 1 --chunk-bytes 4194304
  --small-threshold 65536 --failure-domain host`.
- Controllers: `--failure-domain host --unhealthy-after-secs 20
  --health-interval-secs 5 --gc-interval-secs 10 --gc-grace-secs 30
  --min-orphan-age-secs 90 --reconcile-interval-secs 30
  --admission-horizon-secs 60 --admission-dwell-secs 10
  --scrub-interval-secs 0` (background scrubbing off: scrubs are run by the
  driver), lease 10 s (default), no `--auto-repair` (default).
- Gateways: `--allow-anonymous`, same profile flags as the groups,
  `--lease-secs 60`.
- Transport: plaintext for node RPCs and FoundationDB
  (`ARCA_INSECURE_PLAINTEXT=1 ARCA_FDB_INSECURE_PLAINTEXT=1`), as in
  `two-host.sh`. mTLS was not set up: the TLS paths are **not covered**.
- Client: Python standard library, plain HTTP, unsigned requests, 4
  threads, 160 keys (40 per thread, so operations on one key are
  sequential), object sizes 1 KiB, 4097 B, 64 KiB ± 1, 300 kB, 1 MiB,
  4 MiB ± 1, 9 MiB, 16 MiB; PUTs paced at 2 MiB/s during the fault steps;
  per-request timeout 60 s (90 s in step 6). No multipart uploads (**not
  covered**).

### The ledger and how outcomes are judged

Every request is recorded (start/end time, gateway label, key, size,
SHA-256 of the body, HTTP status, outcome). Per key the client keeps the
set of states the key may be in:

- PUT 2xx (*ack*) or DELETE 2xx: the set becomes {that body} / {absent}.
- 5xx, timeout, or connection lost after sending (*indeterminate*): the
  body (or absent) is **added** to the set (an S3 5xx does not prove the
  write was not applied: `write.rs:362-411`, `write.rs:575-581` answer 503
  for a commit whose outcome could not be resolved).
- Connection refused before sending: no change.
- A GET must answer a member of the set: 200 with exactly the length and
  SHA-256 of a candidate body, or 404 when absent is a candidate. Anything
  else is a **violation**. (Bodies are compared by length and SHA-256, not
  byte by byte; generated deterministically from a seed.)

**Any violation in any step is a FAIL.** Steps 6 and later "collapse" a
key's set to what the verification read once FoundationDB is back
(after recovery the outcome of every earlier commit is decided).

## Expected behaviour from the code

- **Placement.** `create_groups_from` (`crates/controller/src/groups.rs:99-154`)
  creates `count` EC groups and, because the small-object policy is on,
  `count` replication groups `1 + (replicas - 1)` with 3 replicas
  (`groups.rs:114-120`, `crates/cli/src/main.rs:143-146`). Members are the
  best device per distinct `host` value, ranked by group count then node id
  (`crates/placement/src/lib.rs:78-130`), counting the groups created so
  far (`groups.rs:34-54,149`). Expected: 4 groups, each with exactly one
  member per host; with ids 1..6 in registration order, the members are
  {a0, b0, c0} or {a1, b1, c1}.
- **Writes.** A chunk is acknowledged only when **every** shard of its group
  is stored (`crates/gateway/src/cluster/write.rs:989-1076`, "m_ack = m");
  on a node failure the gateway retries the chunk on another group, up to 4
  attempts, never the same group twice (`write.rs:853-929`); only `Active`
  or `Repairing` groups are chosen (`write.rs:955-963`).
  Consequences: with one storage node down, writes go to the group(s)
  without it and succeed; with one host's storage nodes down, every group
  lacks a member and **every PUT must fail** (503); the cluster does
  **not** accept writes through the loss of a host.
- **Reads.** Data shards are fetched first, parity only if fewer than `k`
  arrived; fewer than `k` is `Unreadable` (`crates/tiering/src/durable.rs:117-191`);
  a degraded read is counted and reported to the repair queue
  (`crates/gateway/src/cluster/read.rs:676-706`). Expected: reads survive
  the loss of one member per group, including one host's storage nodes.
- **Host-failure tolerance, as far as it goes.** Data on storage nodes
  tolerates one host for reads only. FoundationDB is a single process on
  host A: host A is a single point of failure for everything. No host was
  actually powered off or cut from the network.
- **Controller takeover.** Lease 10 s (`main.rs:723-725`), renewed every
  lease/3; a follower tries to acquire every lease/3 and succeeds once
  `lease_until_ms` has passed (`crates/controller/src/process.rs:354,393-417`,
  `crates/metadata/src/ops/leader.rs:79-114`). After SIGKILL of the leader
  the other controller must lead within about 10 + 3.3 s; rule: **≤ 20 s**.
  Controllers are not on the request path; gateways keep admitting writes
  on a stale admission record for 5 minutes
  (`crates/gateway/src/cluster/admission.rs:52`): expected 0 client errors.
- **Node down / return.** A node not seen for `--unhealthy-after-secs`
  counts as unhealthy (`process.rs:1577-1581,1777-1792`). Without
  `--auto-repair` no member is replaced (`process.rs:2703-2726`).
- **Wiped disk.** A node that acknowledged an identity and comes back
  without one is quarantined ("an emptied or replaced disk",
  `process.rs:1710-1711,1724-1732`). `admin replace-member` rebuilds the
  member onto a healthy non-member whose `host` differs from the remaining
  members' (`process.rs:3174-3218`, `placement/src/lib.rs:139-158`): the
  only candidate is the other node of the same host (b0 for b1).
- **FoundationDB unavailable.** Every transaction times out after 10 s
  (`crates/metadata/src/fdb.rs:133,200-221`); a commit whose reply is lost
  is resolved by re-reading or fenced by aborting the generation
  (`write.rs:362-411,554-583`). Expected: explicit 5xx or client timeouts,
  never wrong bytes; acked writes survive.
- **Scrub.** Findings are counted in 8 classes
  (`crates/metadata/src/ops/integrity.rs:16-48`). `UnexpectedShard`
  includes valid shards no live generation references
  (`crates/controller/src/integrity.rs:672-676,750-755`), which failed or
  aborted writes and retried chunks leave behind until GC/reconciliation:
  it is **reported, not judged**. All other classes are "damage".

## Steps and pass/fail rules

"Window" = requests that started after the fault and finished before the
recovery action. Requests in flight at the fault instant are reported, not
judged (beyond the violation rule).

| Step | Action | PASS requires |
| --- | --- | --- |
| 0 setup | start everything | all processes running; a PUT and DELETE succeed through both gateways within 240 s |
| 1 placement | `admin status`, `check-config` | 6 nodes; 2 `rs-gf8-v1 2+1` + 2 `replication-v1 1+2` groups, Active; one member per host in every group; members {a0,b0,c0} or {a1,b1,c1}; a leader ctl-a or ctl-b |
| 2 S3 basic | 400 ops (PUT/GET/DELETE) via both gateways, every size through both, then GET every key | 0 errors, 0 violations, every size acked on both gateways, deleted keys answer 404 |
| 3a node kill | load; SIGKILL b0; 15 s; restart | window: 0 errors, PUTs acked, GETs 200; 0 errors from 10 s after restart; repair queue drains (0 unrecoverable, 0 failed); verify clean |
| 3b gateway restart | load; SIGKILL gw-b; 10 s; restart | gw-c 0 errors; gw-b 0 errors from 5 s after restart; verify clean |
| 3c host B nodes down | load; SIGKILL b0 and b1 (one command); 20 s; restart | window: GETs 0 errors, **no PUT acked**, PUTs in the window fail (status or error recorded); rerun: no PUT *started* while both were down is ever acked, whenever it finished; 0 errors from 10 s after restart; queue drains; verify clean |
| 4 controller takeover | load; 3 × (SIGKILL leader, poll leader record, restart it) | each takeover ≤ 20 s by the other controller; restarted one runs; 0 client errors; verify clean |
| 5 node return | load; SIGKILL a1; ~45 s (> 20 s unhealthy); restart | leader metric `nodes_unhealthy` = 1 during, 0 within 60 s after (rerun: counted from the restart; r1–r5 polled from about 25 s after it, for 60 s); groups unchanged and Active; window and post-restart 0 errors; queue drains; scrub of a1's groups 0 damage; verify clean |
| 6 FDB unavailable | load; (a) SIGSTOP fdbserver 30 s, SIGCONT; (b) SIGKILL, 30 s, restart same data dir | 0 violations; PUT through both gateways succeeds within 240 s after; next 30 s 0 errors; every arca process still running; a leader; verify (all acked PUTs read back, indeterminate ops resolve to a candidate) |
| 7a scrub + repair | r1–r2: stop c1, flip 3 shards (`storage-node corrupt-shard --pick`), start, scrub its groups; from r3: flip chunk 0 of three current objects (generation from `integrity verify-object`) | r1–r2: ≥ 1 ChecksumMismatch; from r3: one damage finding per flipped shard, `verify-object --decode` exit 0 for each; rerun: the queue also 0 unrecoverable and 0 failed; repair queue empties within 300 s; re-scrub 0 damage; verify clean |
| 7b wipe + replace | stop b1, delete its directory, start; then `replace-member` for each of its groups | b1 quarantined within 90 s; GETs still answered; both groups Active within 900 s with b0 in place of b1, one member per host; scrub of all groups 0 damage; verify clean |
| 7c final | scrub all groups, integrity status, verify-manifests, full read-back | 0 damage findings, 0 unrecoverable tasks, verify-manifests exit 0, every key reads back as a candidate, 0 violations in the whole ledger |

A FAIL stops the sequence; later steps are NOT RUN.

## Not covered

Network partitions or packet loss between hosts, power loss, a whole host
going away (only processes were killed), disk faults other than three
flipped shards and one deleted directory, FoundationDB with more than one
process or its own failover, mTLS, multipart uploads, versioning, the cache
tier, `--auto-repair`, rejoining the wiped node (`node rejoin
--fresh-identity`), long runs, performance, and capacity pressure.

#### Product finding: member replacement ignores the failure domain (R-119)

`admin replace-member --group 2 --index 1 --yes` (same for group 4) on a
group `[a1, b1, c1]` (labels `host=a|b|c`, controllers
`--failure-domain host`) with b1 quarantined: the leader logged `member
replacement group=4 index=1 node=1 why="replace request"` and the groups
ended `Active members [4, 1, 6]` = a1, a0, c1 (r3 and r5, identical). The
group no longer survives the loss of host A; the plan expected b0.

Likely cause (code reading, not verified by a fix): `choose_for`
(`crates/controller/src/process.rs:3174-3218`) removes every current member
from `candidates` (3209-3213) and passes that list to `choose_replacement`,
which derives the excluded domains by looking the remaining members up in
the same list (`crates/placement/src/lib.rs:144-152`). It never finds them,
so no domain is excluded and the best-ranked candidate (lowest group count,
then lowest id: a0) is chosen. The same function serves auto repair, drains
and the dry-run planner (`process.rs:2856`, `crates/controller/src/plan.rs:223,239`).

Reproduction: the setup above (6 nodes, 2 per host, `create-groups --count 2
--k 2 --m 1 --failure-domain host`), stop b1, empty its `--dir`, start it,
wait for `admin node list` to show it quarantined, run `admin replace-member
--group <its group> --index <its index> --yes`, then `admin status`.

#### Earlier runs and what was changed

- **r1** stopped at step 5: `unhealthy_metric_during [ctl-b, null]`. The
  driver's `grep -E '^name( |{)'` is not a valid pattern, so the metric was
  never read (the controller served it). Fixed the pattern. Everything
  before step 5 passed.
- **r2** stopped at step 7a: three shards chosen by `corrupt-shard --pick
  7/23/61` (groups 2, index 2) were quarantined by the node at start-up, but
  scrub reported no damage in any class and nothing to repair; verify clean.
  The picked chunk ids carry the earliest generations (step 2), most of
  whose objects were overwritten or deleted later and stay on disk for the
  reclaim retention (`main.rs:628-636`), so `--pick` most likely hit
  unreferenced records: 16 of the 17 matching acknowledged PUTs were
  overwritten later, one key was not; the flipped shards were parity
  (index 2), so a clean read says nothing about them, and no `--decode`
  check was run. The controller logged `reconcile pass deleted=3` 9 s
  after the node's start, before the scrub, and scrub reports a
  quarantined shard of its member as damage whether referenced or not
  (`crates/controller/src/integrity.rs:678-707`, before the reference
  check at 750): consistent with unreferenced shards removed by
  reconciliation, **not proven**. Not counted as a driver bug. The step was
  changed to corrupt chunk 0 of three objects known to be current
  (generation from `integrity verify-object`), with a stricter rule (one
  damage finding per flipped shard and verify-object --decode exit 0); r3
  and r5 then found all three.
- **r3** stopped at step 7b with the product finding above; in addition the
  driver read the quarantine from `admin status`, which prints only
  membership records, so `quarantined_after_s` was null although the
  controller logged the quarantine 3 s after the restart. Changed to `admin
  node list`.
- **r4** stopped at step 3c: 5 PUTs acked, all started 0–0.19 s after the
  driver's window start. The window started at the first kill (`min`), but
  b1 was killed by a second ssh command after b0. The plan's expectation
  (no group whole, `write.rs:1067-1076`) holds only once both are down, so
  the window was mis-measured, not the expectation. Changed to one `kill`
  for both pids and the window from after it; r5 then showed 0 acks among
  30 PUTs.

The plan's expectations were not changed; the 7a injection was (r3), and
three checks were made stricter for the rerun (independent review).

Known looseness of the ledger client (independent review): outside step
6's collapse, a key keeps every indeterminate body as a candidate until
its next acknowledged PUT or DELETE, so a read going back from a newer
candidate to an older one is accepted (a stale read among candidates is
not detected; a wrong body is). In r5 every multi-candidate key resolved
to the earlier body or absent.
