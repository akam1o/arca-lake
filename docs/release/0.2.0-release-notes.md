# arca-lake 0.2.0 release notes (draft)

Draft for the GitHub Release text; not published. Date: TBD.

0.2.0 is the second **experimental pre-release** of arca-lake, for
evaluation and development. It is **not production-ready**: do not store
data you cannot afford to lose. What was verified for it, and what was
not, is in the [0.2.0 readiness](0.2.0-readiness.md) tracker; the full
list of changes is in the [changelog](../../CHANGELOG.md).

## Artifacts

- `arca-lake-0.2.0-x86_64-unknown-linux-gnu.tar.gz` and its `.sha256`: a
  Linux x86_64 (glibc) binary built with
  `cargo build --release --locked -p arca-lake --features fdb`, with
  `LICENSE`, `NOTICE`, `THIRD-PARTY-LICENSES.txt` and `BUILD-INFO.txt`
  ([building](building.md)). It needs the FoundationDB 7.3 client
  library on every host that runs it.
- No container image, no crates.io package, no macOS, aarch64 or Windows
  binary ([supported platforms](../guide/supported-platforms.md)).

## Highlights

- **Shard write ownership (R-117, ADR-0037).** A storage node that has
  adopted no incarnation refuses every shard write; every write names
  its target node, and another node refuses it. Once the cluster is at
  metadata schema 5, writes carrying no incarnation or naming no node
  are refused too.
- **Failure domains recorded per group (R-119, ADR-0038).** Every member
  move uses the label recorded on the group, not the controller's
  `--failure-domain`.
- **Scrub shard classes (ADR-0036).** Records kept for reclaim are
  `retained`, no longer unexpected shards; shards held by an operation
  in progress are `in_flight`; shards that cannot be classified are
  `unclassified` and counted as errors.
- **Repair and tiering fixes.** A repair task for a migration target's
  damaged shard is kept until the switch (R-120); tiering resets an
  access record only after the whole move (R-118, ADR-0040).
- **Hot keys (R-112, ADR-0041).** Writes to one key through a gateway
  take turns; `--commit-queue off` restores the 0.1.0 behaviour.
- **S3 request checks.** `Content-MD5` and `x-amz-checksum-*` of XML
  request bodies are verified (`400 BadDigest`, `InvalidDigest`,
  `InvalidRequest`); body verification failures are client errors
  (`XAmzContentSHA256Mismatch` and others) instead of `500`; re-creating
  one's own bucket is `409 BucketAlreadyOwnedByYou`.

## Compatibility

- Metadata schema 5 (reads 4–5). A new 0.2.0 store starts at 5. Wire
  protocol 4 (accepts 3), metadata record version 2, segment format 2
  and storage record version 1 are unchanged from 0.1.0; the new
  protobuf fields are additive and ignored by 0.1.0.
- 0.1.0 is the only supported upgrade predecessor. Stores of schema 3 or
  below (development commits before 0.1.0) are refused: upgrade them to
  0.1.0 and finalize first.

## Upgrading from 0.1.0

The full procedure, with its checks, is in
[operations: upgrading from 0.1.0 to 0.2.0](../guide/operations.md#upgrading-from-010-to-020).
In summary:

1. Take a backup and read these notes.
2. Upgrade the storage nodes, one failure domain at a time.
3. Upgrade the controllers, followers first, the leader last.
4. Record the failure domain of the groups 0.1.0 created:
   `arca-lake admin group set-failure-domain --all-unrecorded --label <label>`
   (first with `--dry-run`), with the label the groups were created
   with; until then no member of those groups is moved, including the
   repair of a failed one
   ([details](../guide/operations.md#upgrading-from-010-record-the-groups-failure-domains)).
5. Upgrade the gateways (drain, restart, return).
6. Stop every tool that writes shards without an incarnation (0.1.0
   `nodebench`, 0.1.0 CLI tools).
7. Check `admin status --versions`: no line may end in `below-schema-5`.
8. Run `admin upgrade finalize --wait`. It is refused while any 0.1.0
   (or unknown) process or node takes part, or a group's failure domain
   is unrecorded.

Until the finalize reaches its cut-off, any process can return to 0.1.0
and `admin upgrade cancel` withdraws the request.

## After the finalize

The finalize is one-way. After it:

- 0.1.0 controllers and gateways refuse to start; a 0.2.0 leader logs and
  counts any that still runs (`arca_controller_procs_below_schema`).
- A 0.1.0 storage node still starts, but the 0.2.0 leader quarantines it
  before sending it anything, gateways and the controller count no
  shard write to it, `--auto-repair` moves its members away, and
  `admin node rejoin` refuses it until it runs 0.2.0.
- Storage nodes refuse shard writes that carry no incarnation or name no
  node.
- Restoring a backup taken before the finalize does not bring 0.1.0
  back: the restored metadata is raised to schema 5.
- 0.1.0 `admin` commands must not be run: they do not check the schema
  gate and know none of the 0.2.0 keys.

## Known limitations

- Before the finalize (an upgraded cluster at schema 4), the 0.2.0
  protections are degraded: shard writes without an incarnation are
  accepted and counted, and a 0.1.0 controller that leads moves members
  by its `--failure-domain` flag.
- The incarnation is not a secret: use one CA or trust domain per
  cluster; plaintext is for tests only.
- 0.1.0 storage nodes do not report retirement: in a mixed cluster
  their retained records are `unclassified` scrub errors.
- The commit queue raises the acknowledged latency of writes to a hot
  key (p50 about 450 ms, p99 about 1.7 s with 64 writers on one key);
  its gain was measured for the whole release against the 0.1.0 tag,
  not for the queue alone.
- DeleteObjects without any digest is accepted; an empty `Content-MD5`
  is treated as absent.
- Not verified: long-duration operation, physical devices and power
  loss, production-scale load. The three test VMs share one
  virtualisation host. See [known limitations](../guide/known-limitations.md)
  and the [risk register](../architecture/risks.md).
